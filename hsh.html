ERD(Entity Relationship Diagram)

ERD

홈스윗홈 서비스의 ERD는 사용자를 중심으로 커뮤니티, 채팅, 정산, 주문 및 결제, 상품, 알림 도메인이 연결되는 구조로 설계되었습니다.

Settlement Domain

정산도메인은 주문건별 정산내역 데이터를 가지고, 주문건별 정산내역 기반으로 집계된 데이터를 가집니다.
집계된 데이터는 기간별로 구분하여 일별, 주별, 월별, 연별 집계 정산 내역 테이블로 분리해 설계했습니다.

IA(Information Architecture)

서비스 구조도

홈스윗홈 서비스는 메인 페이지를 중심으로 커뮤니티, 채팅, 회원, 판매자 정보, 상품, 알림 기능으로 구성된 서비스입니다.
판매자 정보 페이지에서는 재고 목록, 판매 목록, 정산 페이지를 탭으로 구분되는 구조를 가지며,
제가 담당한 정산 기능은 판매자 정보 페이지 하위에 포함되어 있습니다.
IA를 통해 서비스 전체 구조를 먼저 정의한 후, 각 페이지 간 역할과 책임을 명확히 구분하여 기능별 구현과 화면 설계를 진행했습니다.

Arichecture

정산 아키텍처

사용자가 판매자의 제품을 주문 완료 즉, 결제완료가 된 시점에 정산 배치가 실행이 되면서 해당 주문에 대한 주문건별 정산 데이터가 생성이 됩니다.
결제 취소 또는 환불 요청이 들어오면 요청된 데이터는 정산 취소 처리가 됩니다.
주문건별 생성된 정산 데이터들은 순차적으로 집계 처리가 되는데
일별 집계 -> 주별 집계 -> 월별 집계 -> 연별 집계 순으로 데이터가 생성이 됩니다.
집계가 완료된 주문 건의 정산 상태는 정산 진행중에서 정산 완료 상태로 변경이 됩니다.
배치 스케줄링은 준 실시간 집계 구조를 갖기 위해 10초 단위로 실행됩니다.

Problem & Solution

문제 상황

대량 주문 환경에서 판매자 정산을 준실시간 배치 방식으로 처리하는 기능을 구현하면서,
짧은 주기의 배치 실행 과정에서 정산 데이터의 정합성과 처리 성능을 동시에 고려해야 했습니다.
주문 데이터는 DB에 누적되며, 배치 실행 시점마다 일정 시간 범위 내의 주문을 조회해 주문건 정산 데이터를 생성하고,
이후 일·주·월·연 단위 집계를 수행하는 구조였습니다.
이 과정에서 배치 재실행이나 처리 지연이 발생할 경우,
이미 정산이 완료된 주문과 신규 주문이 명확히 구분되지 않아 동일 주문이 중복 정산되거나 집계 결과가 일관되지 않는 문제가 발생했습니다.
또한 분당 수만 건의 주문이 유입되는 상황에서, 기존의 정산 생성의 Reader 구조는
orders → order_items → sku → product → seller → grade의 5중 JOIN으로 설계되어,
실제로 필요한 데이터는 일부 컬럼뿐임에도 DISTINCT와 조건절이 포함되어 수천만 Row가 조회되며,
반복적인 DB 접근으로 인해 배치 수행 시간이 목표 SLA를 초과되어, 처리 성능과 안정성이 불안한 상황이 발생했습니다.

해결 방법

정산 대상 주문을 시간 조건만으로 판단하던 기존 흐름에서
주문 엔티티에 정산 처리 여부를 확인하는 플래그를 추가하였습니다.
정산 처리 여부를 기준으로 데이터를 명확히 분리하며 배치 처리 흐름을 재정리했습니다.
배치 실행 시에는 정산 미처리 상태의 주문만 조회하도록 조건을 분리하고,
정산 생성 단계에서 주문별 정산 상태를 즉시 갱신해 이후 배치 실행에서도 동일 주문이 다시 처리되지 않도록 했습니다.
또한 정산 생성 및 집계 과정에서 Reader를 2단계로 재설계했습니다.
Step 1: Cursor기반으로 배치 처리 대상 주문 ID만 조회하여 불필요한 JOIN과 전체 컬럼 조회를 피했습니다.
Step 2: Step1에서 조회한 ID리스트를 기반으로 실제 정산에 필요한 컬럼만 조회하도록 구조를 변경했습니다.
집계 단계에서는 애플리케이션 단 반복 처리 대신 DB 그룹 연산 기반 집계 방식으로 변경해, 배치 수행 시간과 처리 성능을 안정적으로 개선했습니다.
